# ROBOTIS 직무 질문·답변 은행

목표 직무: [휴머노이드 시스템 소프트웨어 엔지니어](https://robotisrecruiter.ninehire.site/job_posting/aE8A4gYI)

## 1. 왜 로보티즈와 이 직무인가요?

“TurtleBot3를 사용하면서 ROS 2 소프트웨어가 센서, OpenCR, 모터 제어기와 만나는 지점의 중요성을 직접 경험했습니다. 저는 알고리즘 한 부분보다 bring-up, 통신, 안전 정지, 복구까지 이어지는 시스템 소프트웨어를 개발하는 데 강점과 흥미가 있습니다. 휴머노이드 시스템 소프트웨어 직무에서 하드웨어와 상위 동작 사이의 안정적인 실행 기반을 만드는 개발자로 성장하고 싶어 지원했습니다.”

## 2. 휴머노이드를 직접 개발한 경험이 있나요?

“직접적인 휴머노이드 개발 경험은 아직 없습니다. 대신 TurtleBot3에서 ROS 2 실기기 통합과 안전 정지를, 로봇팔에서 액추에이터 제한·기구학·Pi–MCU 분산 제어를 경험했습니다. 휴머노이드는 관절 수와 실시간성, 안전 요구가 더 크기 때문에 같은 경험이라고 주장하지 않겠습니다. 다만 센서·제어기·상위 노드의 책임을 분리하고 측정 가능한 acceptance test를 만드는 접근은 확장해 적용할 수 있습니다.”

## 3. DYNAMIXEL SDK 경험은 어느 정도인가요?

“TurtleBot3의 OpenCR 내부 경로를 통해 DYNAMIXEL을 사용했지만 SDK로 직접 read/write와 오류 복구를 구현한 증거는 아직 없습니다. 그래서 보유 역량으로 과장하지 않고 부족 항목으로 공개했습니다. 다음 실기기 프로젝트에서는 실제 모터 모델과 연결 경로를 먼저 확인하고, 명령·상태 read/write, timeout, 통신 복구를 반복 시험해 증명할 계획입니다.”

## 4. `ros2_control`을 직접 구현해 봤나요?

“hardware interface를 직접 구현한 경험은 아직 없습니다. 팀 시스템의 `gz_ros2_control`은 배경으로만 이해하고 제 기여로 주장하지 않습니다. command/state interface, controller lifecycle, read/write 주기를 학습하고 있으며, 실기기에서 재현 가능한 패키지와 테스트가 완성된 뒤에만 포트폴리오 역량으로 표시하겠습니다.”

## 5. 가장 어려웠던 실기기 장애는 무엇이었나요?

“TurtleBot3에서 `/scan` publisher는 존재하지만 데이터가 나오지 않았던 문제입니다. QoS나 ROS parameter를 무작정 바꾸지 않고 물리 입력, driver, ROS graph 순으로 계층을 나눴습니다. raw UART에서 수신이 없음을 확인한 뒤 LDS-02 TX 연결 이탈을 찾았고, 복구 후 5초간 44,105 bytes와 header 940개를 확인해 센서부터 `/scan`까지 검증했습니다.”

## 6. 네트워크가 끊기면 로봇을 어떻게 안전하게 멈추나요?

“상위 관제의 연결 상태만 믿지 않고 각 경계에 timeout을 둡니다. TurtleBot 프로젝트에서는 deadman, gateway, Zenoh 경로에서 stale command를 제거하고 최종 0 속도 명령이 전달되는 시간을 측정했습니다. 결과는 0.301~0.305초였고 자동 재개는 허용하지 않았습니다. 로봇팔에서는 ESP32가 마지막 명령 시간을 독립적으로 감시해 timeout 후 relax합니다.”

## 7. C++와 Python은 어떻게 나눠 사용했나요?

“주기가 중요하고 최종 안전 책임을 갖는 watchdog은 C++ 또는 MCU 쪽에 두고, 작업 orchestration, gateway, 비전, 진단 도구는 Python으로 빠르게 구성했습니다. 언어 선호보다 지연, 장애 격리, 배포 위치와 유지보수성을 기준으로 나눕니다.”

## 8. ROS 2 문제를 어떤 순서로 디버깅하나요?

“먼저 전원·배선·포트와 raw data를 확인하고, 다음으로 driver 프로세스와 parameter, 그다음 node/topic/QoS와 TF, 마지막으로 Nav2 같은 상위 동작을 확인합니다. 각 단계에서 정상·비정상 경계를 좁히는 명령과 로그를 남겨 같은 장애를 재현하고 복구할 수 있게 합니다.”

## 9. 팀 프로젝트에서 본인의 기여는 무엇인가요?

“AIP Swarm에서 제가 맡은 것은 카메라 비전, 웹 관제, 서브 차량 구동 연동입니다. 팀 ROS graph와 launch/config 통합은 공동 수행이고, Gazebo·Nav2 전체 구성과 `gz_ros2_control`은 팀 시스템입니다. 공용 저자 커밋 수를 개인 기여 증거로 쓰지 않고 코드와 인터페이스 단위로 설명합니다.”

## 10. 성능 수치를 어떻게 신뢰할 수 있나요?

“수치마다 조건과 증거를 같이 제시합니다. 예를 들어 0.301~0.305초는 네트워크 단절부터 최종 정지 명령까지의 특정 경로 측정이고, 로봇팔 23 FPS는 640×480 RGB 카메라 조건입니다. mock 데이터의 F1 1.00은 일반화 성능이 아니라고 명시합니다. 조건을 재현할 수 없으면 수치를 대표 성과로 사용하지 않습니다.”

## 11. 입사 후 가장 먼저 보완하고 싶은 것은 무엇인가요?

“DYNAMIXEL SDK와 `ros2_control`을 실제 액추에이터와 연결해 command/state interface, controller lifecycle, timeout과 복구를 코드와 로그로 검증하고 싶습니다. 기존 OpenCR 제어 경로와 충돌하지 않는 시험 구성을 먼저 만들고 작은 단위부터 acceptance test를 쌓겠습니다.”

## 12. 실패하거나 미완료된 부분을 말해보세요.

“TurtleBot Fleet Ops는 두 대 운영을 목표로 했지만 대표 실기기 acceptance는 TB1 중심이고 TB2 자동 할당은 완료 범위가 아닙니다. Camping Safe Guard도 모델 정확도와 MCU 자원 사용량을 재현 가능한 보고서로 정리하지 못했습니다. 포트폴리오에는 이를 숨기지 않고 한계와 다음 검증 항목으로 표시했습니다.”
